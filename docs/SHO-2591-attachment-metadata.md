# SHO-2591: task attachment metadata and development stub only

Source of truth: [BTF SHO-2591, 19.2a / description v3](https://backlogtothefuture.aplyd.org/aplyd/issue/SHO-2591).

This is an incomplete, storage-neutral task-file slice. Keep unmerged or feature-off until NJ decides the object store, region, keys, limits, versioning and backups. It does not implement deal files (19.2c, blocked on CRM PR7), real storage, preview or malware scanning. No provider, account, credential or infrastructure is provisioned.

`FF_ATTACHMENTS` defaults off. Off leaves task and project Trash payloads without attachment UI flags; all attachment routes and attachment Undo return 404, the concierge tool is absent, and Activity hides attachment actions and their Undo rows. Existing task deletion still cleans up any object keys before deleting rows, even when the UI is off.

For local development or isolated unit tests only, set `FF_ATTACHMENTS=true` and `ATTACHMENT_STORE=test-stub`. The supplied in-memory adapter refuses every operation when `NODE_ENV=production`; it cannot be a production store. Stub content disappears on restart. Metadata can consequently outlive stub objects. Use only disposable test data. There are no public, signed or cached download links: the app checks the current task/project access on every request and streams a forced-download response. Editors and Leaders can add/remove; Viewers can download. Deal task files are deliberately unavailable.

The conservative test allowlist is PDF only, with both `.pdf` extension, `application/pdf` MIME and a `%PDF-` header. Header validation is not a malware scan. The UI states no scanning. The 25 MiB/file and 10 active files/task limits are provisional test values, not an approved production policy: FR19.2-02 leaves these and the broader allowlist to NJ. Validation and cap rejections use HTTP 400 with `file_too_large`, `too_many_files` or `type_not_allowed`. Multipart input is bounded even without a truthful Content-Length; invalid files and limit rejects create neither object nor row. Task-row locks serialize uploads, removals and restores against the cap and purge; upload admission checks project access again after buffering and before storing.

The expand-only migration adds `TaskAttachment`. Storage content is never stored in metadata, action logs, audit logs or concierge inputs. Activity stores only filename plus attachment ID; the concierge's optional `task_files` read returns flattened filenames explicitly wrapped as untrusted data, never bytes/URLs. No chat-upload tool exists.

Removal is soft. Removed files appear in project Trash with days remaining; Restore and Undo retain the same object key. After strictly more than 30 days, purge removes the object before the metadata row. Task purge lists both task and subtask attachment keys, removes their objects before `deleteMany`, and aborts on any storage failure. It locks and rechecks trashed tasks before removal so a concurrent restore cannot revive a task whose objects were purged. Deletion is idempotent at the adapter boundary; a partial object deletion followed by an adapter failure may make some still-retained rows unavailable until retry. The chosen real store must define operational retry/recovery before enabling production.

Validation and release gates: focused unit/security/purge/Undo tests; flag-off HTTP integration in isolated CI; full lint, typecheck and production build. No local database was available, so real database concurrency and an actual storage adapter require additional acceptance after NJ's decision. The production build deliberately cannot test positive stub uploads. No deployment, staging run, release evidence or Done claim is included.
